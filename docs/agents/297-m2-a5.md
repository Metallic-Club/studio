# #297 M2a task A5: metallic_net transport

Branch `studio/297-m2-a5-transport`. Plan: task A5 of the M2a plan; spec
`docs/superpowers/specs/2026-10-30-multiplayer-m2-design.md` sections 3.1 and 7.3.

## Done (tested)
- New crate `crates/metallic_net` (lib.rs is a short module list so A6 can add `wire` etc.): `error.rs` (`NetError`),
  `transport/{mod,limits,conditioner,cert,memory,quic}.rs`, `tests/transport.rs`.
- `Connection`/`Listener` traits (both `Send`), `Channel`, `Incoming`, `CloseReason`, `LinkStats`, `Sequencer`.
- `MemoryNet`: manual clock, discrete-event delivery, per-link conditioner both ways, reliable re-send after one RTT
  (in order per channel; Bulk payloads independent), keep-alives every 2 s, idle timeout 10 s, Hello deadline 2 s,
  server-side limits. Dropping a memory connection models a crashed peer (no close sent).
- QUIC: `QuicServer::bind` (own tokio thread, fresh ECDSA P-256 cert valid 13 days, backdated 1 h for clock skew),
  `QuicClient::connect` (shared client tokio thread, pinned verifier: SHA-256 of the end-entity DER, then signature
  and validity window with the cert as its own trust anchor), `QuicClient::quinn_config` for raw-QUIC tools/tests.
  ALPN `metallic/1`, idle 10 s, keep-alive 2 s, initial MTU 1280, migration on; client may open 1 bidi + 3 uni
  streams (4 total). Frames: tag byte per stream, then LEB128 length + bytes.
- Limits enforced server side: frame > 64 KiB closes with `ProtocolError` (before reading the body); > 120
  datagrams in any 1 s window dropped and counted; datagrams > 1,200 bytes refused on send (`DatagramTooLarge`)
  and dropped on receive; no Control frame within 2 s closes with `Timeout`; a second Control stream or a stream
  with a wrong tag closes with `ProtocolError`. Client side caps incoming frames at 4 MiB.
- `LinkConditioner` on QUIC wraps the server's `AsyncUdpSocket`: loss and delay on send and on receive.
