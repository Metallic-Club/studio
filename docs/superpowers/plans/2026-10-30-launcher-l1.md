# Metallic Launcher L1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `Metallic.exe`, a native Rust Launcher for Windows 11 that shows the Metallic website in a web view, gives that site (and only that site) a small typed bridge, handles `metallic://` links, starts the Metallic player, installs Studio, updates itself, and works before the website exists.

**Architecture:** New crate `metallic_launcher` (lib + bin `Metallic`) in this workspace. It is a `tao` window holding one `wry` web view. Pure logic (deep links, URL policy, bridge, settings, install state) lives in plain modules with unit tests. Platform code (named pipe, registry, tray, WebView2 details) sits in `platform/windows.rs` behind small traits, with a `platform/other.rs` stub, so Linux (WebKitGTK), macOS, mobile, consoles and VR can be added without touching the logic. The Studio updater moves into a shared crate `metallic_update` first. The website itself stays in `Metallic-Club/plateform`.

**Tech Stack:** Rust 1.99 (edition 2024), `wry` 0.57 (WebView2 on Windows, WebKitGTK on Linux later), `tao` (the window crate wry is built and tested with), `tray-icon` + `muda` (tray and its menu), `url`, `serde`/`serde_json`/`toml`, `windows` (named pipes, registry, message box), `sha2`, `keyring` (Credential Manager), `velopack` 1.3.39-g8d2844f (via `metallic_update`), `ureq` 3.

**Spec:** `docs/superpowers/specs/2026-10-30-metallic-studio-design.md` (sections 5, 8, 10) and `docs/research/2026-10-30-platform-architecture.md` (sections 1.3-1.6, 1.9, 3.5). Website side: `Metallic-Club/plateform` `docs/superpowers/specs/2026-10-30-platform-design.md` (D13, D14, 9.1, 9.9, 10) and its `api/openapi.yaml`.

## Decisions this plan makes (with reasons)

Already decided by the owner and not reopened here: native Rust Launcher, crate `metallic_launcher`, exe `Metallic.exe`,
real website in a web view adapted per device, `metallic://` registered per user in HKCU, the Launcher starts
`metallic-player` with the URI, no passwords in native apps, Velopack updates from GitHub Releases, Windows 11 first.

| Topic | Decision | Why |
|---|---|---|
| Web view | **`wry` 0.57 + `tao`, not full Tauri** | wry is Tauri's own web-view layer (MIT OR Apache-2.0): WebView2 on Windows, WebKitGTK on Linux, WKWebView on macOS/iOS, Android WebView. Full Tauri adds its config/codegen build, its own bundler and updater (overlapping Velopack), and a large IPC/plugin system for a bridge that has eleven commands. Moving up to Tauri later stays possible because the web view is the same |
| WebView2 runtime | Evergreen runtime, not bundled. Setup is packed with `vpk pack --framework webview2`, so the installer adds it when missing (per user, no admin). At start, `wry::webview_version()`; if it fails, a native message box explains and offers Microsoft's download page | Windows 11 ships the Evergreen runtime as part of the OS; Microsoft installed it on eligible Windows 10 devices, but "a small number" still lack it and Microsoft recommends apps distribute it ([distribution](https://learn.microsoft.com/microsoft-edge/webview2/concepts/distribution), [evergreen vs fixed](https://learn.microsoft.com/microsoft-edge/webview2/concepts/evergreen-vs-fixed-version)). Velopack lists `webview2` as a `--framework` prerequisite ([bootstrapping](https://docs.velopack.io/packaging/bootstrapping)). A fixed-version runtime adds well over 100 MB and makes us responsible for its security patches |
| Bridge | Eleven typed, allow-listed commands, JSON with `deny_unknown_fields`, checked in Rust against the sending page's URL on every message, capability set per origin (site / bundled pages / anything else = nothing). The JS shim is injected into the main frame only | wry's IPC handler receives `Request<String>` whose URI is the page that sent it; `with_initialization_script_for_main_only` keeps iframes out ([wry docs](https://docs.rs/wry/0.57.1/wry/struct.WebViewBuilder.html)) |
| Launcher detection by the site | UA suffix ` MetallicLauncher/<version> bridge/1` for server rendering, `window.metallic` for the client; neither is a security boundary | Matches platform spec 9.1 |
| Offline / unavailable / dev screens | Bundled HTML pages served from inside the exe on a custom protocol `metallic-app` (on Windows wry serves it as `http://metallic-app.localhost/`), styled with the shared token CSS. The only truly native UI is the "WebView2 missing" message box | One rendering path, uses the same tokens as the site, testable without a window |
| Sign-in | Platform device flow (RFC 8628, client `metallic-launcher`, scopes `profile play`), browser opened on `verification_uri_complete`; tokens in Credential Manager; the web view gets a cookie session through a one-time handoff code (new platform endpoint, see the plateform issue) | Platform spec D14 and the existing endpoints `/v1/oauth/device/code`, `/v1/oauth/token`, `/v1/oauth/revoke`; Studio's `github_auth.rs` is the pattern |
| Player | Shipped inside the Launcher's Velopack package (same version, lock-step), started as `metallic-player.exe <canonical metallic://play URI>` | Architecture doc 1.5/1.6: Launcher and Player must release together |
| Studio | Installed on demand: the Launcher downloads `MetallicStudio-<channel>-Setup.exe` from Studio's release, verifies its SHA-256 against the GitHub asset digest, runs it | Studio is its own Velopack app and keeps its own updater |
| Releases | Same repo, tags `launcher-vX.Y.Z-<channel>`, Velopack channel `launcher-<channel>`, packId `MetallicLauncher` (installs to `%LOCALAPPDATA%\MetallicLauncher`) | Keeps Studio's `vX.Y.Z-<channel>` feed and `releases.<channel>.json` untouched |
| Data | Settings `%APPDATA%\Metallic\Launcher\settings.toml` (env `METALLIC_LAUNCHER_CONFIG_DIR` overrides); WebView2 profile and downloads `%LOCALAPPDATA%\Metallic\Launcher\` | Same pattern as Studio (`%APPDATA%\Metallic\Studio`); never inside Velopack's `current\`, which updates replace |
| Site address | Compiled from `config/launcher_site_origin.txt` (placeholder `REPLACE_WITH_SITE_ORIGIN` until the production domain exists; then the Launcher shows "not configured" offline page) | Same pattern as `config/github_app_client_id.txt`; no host names guessed in code |

## Review Focus

Security first: the bridge and the protocol handler are the attack surface.

1. **Wrong page calls the bridge.** A lookalike host (`metallic.example.evil.test`, `metallic.example@evil.test`), an `http://` downgrade of the site, a different port, an iframe, or a page the view navigated to after sending a request must never run a command or receive a reply. Tests: Task 2 `lookalike_hosts_are_not_the_site`, Task 4 `other_origin_is_ignored`, `reply_dropped_when_page_changed_origin`, Task 3 smoke `other_origin_page_has_no_bridge`.
2. **Hostile `metallic://` link** (from any web page, email or a second process): quotes and spaces, extra command-line arguments such as `--dev-url`, over-long input, double percent-encoding, a ticket with shell characters. Expected: refused with a log line that does not echo the ticket; the Player receives only the re-serialised canonical URI as one argument, no shell. Tests: Task 2 `rejects_bad_ticket_chars`, `percent_decoding_happens_once`, Task 5 `uri_argument_disables_other_flags`, `player_gets_canonical_uri_as_single_arg`, `garbage_handoff_rejected`.
3. **Dangerous navigation.** `file:`, `javascript:`, `data:`, `blob:`, `ms-msdt:`, `vbscript:`, UNC paths and plain `http:` hosts are blocked; other `https:` hosts open in the system browser only; web-view downloads and permission prompts (camera, microphone, location, notifications) are denied. Tests: Task 2 `dangerous_schemes_blocked`, `other_https_opens_in_browser`, manual check in Task 3 Step 6.
4. **Secrets leak.** Tokens never appear in logs, `Debug`, bridge replies or crash text; the GitHub token is not forwarded when an asset download redirects to another host; a downloaded installer runs only after its SHA-256 matches. Tests: Task 1 `token_never_logged` (moved), Task 6 `token_not_forwarded_on_redirect`, `digest_mismatch_deletes_file`, Task 7 `tokens_never_in_debug_or_logs`.
5. **Broken environment.** Site down, DNS failure, placeholder site address, WebView2 missing, corrupt `settings.toml`, Launcher killed mid-download, update ready while the Player runs. Expected: the bundled offline page (or the WebView2 message box), never a white window, never a half-installed app. Tests: Task 2 `corrupt_settings_fall_back_to_defaults`, Task 3 `start_page_*`, Task 6 `apply_waits_while_player_runs`, `partial_download_is_not_used`.
